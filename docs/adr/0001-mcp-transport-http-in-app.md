# ADR-0001: MCP 전송은 앱 내장 Streamable HTTP

## 맥락

virtual-device-helper는 MCP 서버 역할만 한다. 앱 안에 에이전트를 품지 않고, 외부 에이전트
(Claude Code 등)가 붙어서 가상 기기를 제어한다.

문제는 MCP의 일반적인 전제와 이 앱의 형태가 어긋난다는 점이다. MCP 클라이언트는 보통 서버
프로세스를 직접 실행하고 stdio로 대화한다. 그런데 이 앱은 사람이 화면을 보려고 띄워 두는 GUI
프로세스다. 클라이언트가 또 하나를 실행하면 기기 상태를 쥔 프로세스가 둘이 된다.

동시에, 사람이 앱에서 보는 화면과 에이전트가 만지는 기기가 같아야 한다는 요구가 있다. 화면
스트리밍·로그·툴 호출 타임라인이 한 곳에 모이는 것이 이 앱의 존재 이유다.

## 결정

MCP 서버를 Electron main 프로세스 안에서 Streamable HTTP로 연다.

- 전송 구현은 `@modelcontextprotocol/sdk`의 Streamable HTTP를 쓴다. 직접 만들지 않는다.
- 바인드 주소는 `127.0.0.1` 고정. 외부 바인드 옵션을 만들지 않는다.
- 앱 실행 시 무작위 토큰을 만들고 모든 요청의 `Authorization` 헤더에서 검사한다.
- `Origin` 헤더를 검사해 브라우저에서 온 요청을 거부한다.
- 기본 포트가 점유되어 있으면 다음 빈 포트로 넘어가고, 실제로 열린 포트를 UI에 띄운다.
- 서버 수명은 앱 수명과 같다. 앱이 닫히면 진행 중 요청을 종료 에러로 마감한다.
- 세션은 여럿 허용하되, 한 기기의 명령은 큐 하나로 직렬 실행한다.
- 사람이 클라이언트 설정에 붙일 JSON 조각을 UI에서 통째로 복사할 수 있게 한다.

## 대안

- **stdio 서버를 앱과 분리** — 기기 제어 코어를 독립 패키지로 빼고 클라이언트가 stdio로 직접
  실행한다. 앱 없이도 돌고 CI·헤드리스에서 쓸 수 있다.
  **→ 기각:** 기기를 쥔 프로세스가 둘이 되어 조율이 필요해진다. adb는 머신당 서버 데몬을
  공유하므로 두 프로세스가 같은 기기에 동시에 명령을 보내면 순서를 보장할 수 없다. 사람이 보는
  화면과 에이전트가 만지는 기기를 일치시키는 것이 이 앱의 목적인데, 이 구조는 그 일치를 깬다.
- **stdio 브리지** — 클라이언트가 얇은 stdio 브리지를 실행하고, 브리지가 떠 있는 앱에 소켓으로
  전달한다. 기존 MCP 클라이언트 설정 형식(command + args)에 그대로 맞고 상태는 앱 하나에 모인다.
  **→ 기각:** 배포·버전 관리해야 할 조각이 하나 늘고, 앱이 꺼져 있을 때 브리지의 동작(자동 실행,
  대기, 실패)을 따로 정의해야 한다. HTTP로 얻는 것과 차이가 크지 않다. 기존 클라이언트 설정
  형식과의 호환이 실제로 문제가 되면 그때 이 ADR을 대체한다.

## 영향

**긍정**

- 기기 상태를 쥔 프로세스가 하나뿐이다. 사람이 보는 것과 에이전트가 만지는 것이 항상 같다.
- 배포물이 Electron 앱 하나다. 별도 패키지·바이너리를 관리하지 않는다.
- 툴 호출을 renderer로 흘려 타임라인에 그리는 경로가 프로세스 경계를 넘지 않는다.

**트레이드오프**

- 앱이 꺼져 있으면 툴을 쓸 수 없다. CI·헤드리스 사용은 불가능하다.
- 클라이언트가 URL 기반 MCP 서버를 지원해야 한다.
- 사람이 URL과 토큰을 설정에 옮겨야 한다. UI의 복사 버튼으로 줄인다.

**위험·방어**

- 로컬 포트에 붙는 쪽은 임의 APK 설치, 호스트 경로 읽기, 입력 주입이 가능하다. 루프백 바인드,
  토큰 검사, `Origin` 검사 세 겹으로 막는다. 세 가지 모두 기본값이며 끄는 옵션을 두지 않는다.
- 토큰 누락·오류, 브라우저 `Origin` 요청이 실제로 거부되는지를 테스트로 고정한다.
